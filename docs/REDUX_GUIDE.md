# Redux & RTK Query Guide

This project uses **Redux Toolkit** with **RTK Query** for state management and data fetching. This guide covers the conventions and patterns used throughout the codebase.

## Architecture Overview

```
src/
  store/
    store.ts              configureStore + RootState + AppDispatch
    api/apiSlice.ts       Base createApi (empty endpoints, injected by codegen)
  shared/api/             Generated API slices (authApi, booksApi, etc.)
  features/
    auth/model/           authSlice
    swipe-book/model/     swipeSlice
    track-progress/model/ userSlice
```

**Key principle**: RTK Query is the source of truth for server state. Local slices only hold UI-only state (e.g. swipe index, auth session) or derived views of server data.

## Store Setup

The store is configured in `src/store/store.ts`:

```ts
export const store = configureStore({
  reducer: {
    auth: authReducer,
    swipe: swipeReducer,
    user: userReducer,
    [apiSlice.reducerPath]: apiSlice.reducer,
  },
  middleware: (getDefaultMiddleware) =>
    getDefaultMiddleware({
      serializableCheck: {
        ignoredActions: ["auth/setSession"],
        ignoredPaths: ["auth.session"],
      },
    }).concat(apiSlice.middleware),
});
```

Use `RootState` and `AppDispatch` types from this file when typing hooks or selectors.

## API Layer

### Base API Slice

`src/store/api/apiSlice.ts` defines the base `createApi` with:
- `baseUrl` from `EXPO_PUBLIC_API_URL`
- JWT token injection via `prepareHeaders`
- Shared cache tags (`Library`, `Feed`, `Thread`, `Review`, `User`)
- Empty endpoints (populated by codegen-injected slices)

### Generated API Slices

All API slices live in `src/shared/api/` and are auto-generated from the backend OpenAPI schema:

```
src/shared/api/
  authApi.generated.ts
  booksApi.generated.ts
  challengesApi.generated.ts
  discussionsApi.generated.ts
  libraryApi.generated.ts
  meApi.generated.ts
  reviewsApi.generated.ts
  swipesApi.generated.ts
```

**Never edit generated files directly** — they are overwritten on `npm run codegen`.

### Codegen

```bash
npm run codegen
```

This runs `@rtk-query/codegen-openapi` against the backend's OpenAPI JSON, then applies `scripts/post-codegen.js` for any remaining fixes.

Config: `openapi-config.js` at the project root. Uses `flattenArg: true` so single-arg endpoints generate flat types instead of wrapping in `body:`.

## Working with Queries

### Basic Usage

```ts
const { data, isLoading, error } = useGetBooksFeedQuery({});
```

### Conditional Fetching

Use the `skip` option to avoid fetching until conditions are met:

```ts
const { data } = useGetBooksQuery(
  { q: debouncedQuery, limit: 6 },
  { skip: debouncedQuery.trim().length < 2 }
);
```

### Prefetching

Use `dispatch(api.util.prefetch)` to warm the cache before navigation.

### Refreshing Stale Data on Screen Focus

When a user navigates back to a screen (e.g. after creating a challenge in a modal), the cached data may be stale. **Do not** trigger refetches manually in `useEffect` or `useFocusEffect`. Instead, use the `refetchOnMountOrArgChange` option on the query hook:

```ts
// CORRECT — RTK Query handles refetching automatically
const { data, isLoading } = useGetChallengesQuery(undefined, {
  refetchOnMountOrArgChange: true,
});

// WRONG — manual refetch in an effect is unnecessary and error-prone
useFocusEffect(useCallback(() => { refetch(); }, [refetch]));
```

Setting `refetchOnMountOrArgChange: true` causes the hook to refetch whenever the component mounts (or when arguments change), ensuring the user sees fresh data after mutations or background navigation. For finer control, pass a number (seconds) to only refetch if cached data is older than that threshold.

See [RTK Query docs — Query Hook Options](https://redux-toolkit.js.org/rtk-query/usage/queries#query-hook-options).

## Working with Mutations

### Always use `unwrap()` with `async/await`

RTK Query mutations return a promise that **always resolves** (never rejects) with the dispatched action. To wait for the actual server response and handle errors, you **must** call `.unwrap()`:

```ts
// WRONG — fire-and-forget, errors are silently swallowed
addToLibrary({ bookId: book.id, status: 'want' });
navigation.goBack();

// WRONG — .then() doesn't give you error handling control
patchLibrary({ bookId, body: { status } }).then(() => setLibraryStatus(status));

// CORRECT — async/await + unwrap()
async function handleMarkStatus(status: 'reading' | 'finished') {
  try {
    await patchLibrary({ bookId, body: { status } }).unwrap();
    setLibraryStatus(status);
  } catch {
    Alert.alert('Error', 'Failed to update reading status.');
  }
}
```

### Why `unwrap()`?

From the [Redux Toolkit docs](https://redux-toolkit.js.org/api/createAsyncThunk#unwrapping-result-actions):

> Thunks generated by `createAsyncThunk` will always return a resolved promise with either the `fulfilled` or `rejected` action object inside. The `.unwrap()` property extracts the `payload` of a `fulfilled` action or throws either the `error` or `payload` from a `rejected` action.

Without `unwrap()`:
- The promise **always resolves** — even on server errors
- You can't distinguish success from failure
- UI state updates (like navigation) happen before the server confirms

With `unwrap()`:
- The promise **rejects** on error, so `try/catch` works naturally
- You can show error feedback to the user
- Success-dependent logic only runs after the server confirms

### Mutation Arg Shapes

With `flattenArg: true`, mutation args follow these rules:

| Endpoint type | Arg shape | Example |
|---|---|---|
| Body-only POST | Flat object (matches HTTP body) | `addToLibrary({ bookId, status })` |
| Path param + body | `{ pathParam, body: { ...fields } }` | `patchLibrary({ bookId, body: { status } })` |
| Path param only (DELETE, POST like) | Just the string | `deleteThread(threadId)` |
| Query params | `{ ...params, id }` | `getChallengesByIdLeaderboard({ id, limit })` |

### Error Handling Patterns

**User-facing mutations** (form submissions, destructive actions) — always show an error:

```ts
try {
  await deleteThread(threadId).unwrap();
  navigation.goBack();
} catch {
  Alert.alert('Error', 'Failed to delete the thread. Please try again.');
}
```

**Background mutations** (analytics, swipes) — silently catch:

```ts
try {
  await recordSwipe({ bookId, direction: 'left' }).unwrap();
} catch {
  // Non-critical — silently ignore
}
```

**Optimistic mutations** — use `onQueryStarted` in the API slice definition with `updateQueryData` and rollback on failure. See [Manual Cache Updates](https://redux-toolkit.js.org/rtk-query/usage/manual-cache-updates).

## Local Slices

### When to use a local slice

- **UI-only state**: swipe card index, loading flags controlled by the component
- **Derived server state**: reshaping API response data for display (like `userSlice` extracting stats from `getMe`)
- **Auth session**: Supabase session storage (needs `serializableCheck` exemption)

### When NOT to use a local slice

- **Server data** — use RTK Query queries directly
- **Form state** — use React `useState` unless the form is multi-screen
- **Temporary flags** — use React `useState` or `useRef`

### Reacting to query results

Use `extraReducers` with `matchFulfilled` to sync local state from query results:

```ts
const userSlice = createSlice({
  name: 'user',
  initialState,
  reducers: {},
  extraReducers: (builder) => {
    builder.addMatcher(meApi.endpoints.getMe.matchFulfilled, (state, action) => {
      state.user = transformMe(action.payload);
    });
  },
});
```

## Cache Invalidation

The base API slice defines shared tag types:

```ts
tagTypes: ["Library", "Feed", "Thread", "Review", "User"]
```

Tags are configured via `endpointOverrides` in `openapi-config.js` (not in the backend OpenAPI schema). When a mutation invalidates a tag, all queries providing that tag automatically refetch.

### Tag Map

| Tag | Queries that provide it | Mutations that invalidate it |
|---|---|---|
| `Library` | `getLibrary`, `getLibraryStats` | `postLibrary`, `patchLibraryByBookId`, `deleteLibraryByBookId` |
| `Feed` | `getBooksFeed` | `postSwipes`, `postLibrary` |
| `Thread` | `getThreads`, `getThreadsById` | `postThreads`, `deleteThreadsById`, `postThreadsByIdReplies`, `postThreadsByIdLike` |
| `Review` | `getBooksByIdReviews` | `postBooksByIdReviews` |
| `User` | `getMe`, `getMeBadges` | `postLibrary`, `patchLibraryByBookId`, `deleteLibraryByBookId` |

### Why some mutations invalidate multiple tags

Library mutations invalidate `User` because adding/removing/updating a book can change XP, streak, and reading stats (the backend's `onBookFinished` pipeline awards XP and updates challenge progress). `postLibrary` also invalidates `Feed` because adding a book to the library should remove it from the swipe feed.

### When to use explicit refetch vs. tag invalidation

Tag invalidation handles most cases automatically. Use explicit `refetch()` only when you need to await the fresh data before doing something (e.g. scrolling to the bottom of a thread after posting a reply):

```ts
await postReply({ id: thread.id, body: { body: text } }).unwrap();
await refetch(); // wait for fresh data before scrolling
scrollRef.current?.scrollToEnd({ animated: true });
```

### Adding new tags

1. Add the tag name to `tagTypes` in `src/store/api/apiSlice.ts`
2. Add `endpointOverrides` in `openapi-config.js` with `providesTags` for queries and `invalidatesTags` for mutations
3. Run `npm run codegen`

## Testing

### Mocking API calls

Use `apiSlice` as the import for store wiring. Override endpoints in tests:

```ts
import { apiSlice } from '@store/api/apiSlice';

const store = configureStore({
  reducer: { [apiSlice.reducerPath]: apiSlice.reducer },
  middleware: (m) => m().concat(apiSlice.middleware),
});
```

### Testing slices

Test reducers directly by dispatching actions, or test via the store with `matchFulfilled` matchers.

## Quick Reference

| Do | Don't |
|---|---|
| `await mutation(arg).unwrap()` | `mutation(arg).then(...)` |
| `try/catch` around `.unwrap()` | Fire-and-forget mutations |
| RTK Query for server state | Duplicate server data in local slices |
| `flattenArg: true` in codegen config | Manually edit generated API files |
| `extraReducers` + `matchFulfilled` | Manually sync query data into slices |
| `skip` option for conditional queries | Conditional `if` around hook calls |
